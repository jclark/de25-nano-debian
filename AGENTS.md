# Instructions for agents

This repository takes a Terasic DE25-Nano from source to a running Debian system. You may be
here to build it for someone, or to change the repository. Read `README.md` first: it has the
overall picture, the order of work, and a table of what has and has not been tested. Each
piece's own `README.md` has what it produces, what it needs first, its tools, its source and
its commands.

## Building it for someone

Before starting, check the machine and say what is missing: Docker usable by this user, git,
free disk (about 10 GB for stage 1, 60 GB with stage 2), and for the SD image on x86,
`ls /proc/sys/fs/binfmt_misc/ | grep aarch64`.

Tell the person before a large download. The Quartus image for piece 3 is 17.5 GiB.

Order:

- Pieces 1, 2 and 3 are independent until the last step of piece 3. Start them together, as
  background jobs, and report as each finishes: `u-boot/build.sh`, `kernel/build.sh`,
  `fpga/build.sh` (stage 2 only).
- `fpga/build.sh` needs `out/u-boot/u-boot-spl-dtb.hex` only for its last step. If piece 1 has
  not finished by then it stops with a message; run it again and it carries on.
- `sdimage/build.sh stage1` or `stage2` last.

The scripts fetch sources into `work/` and write results to `out/`. Do not edit what is under
`work/`, and do not change a pinned commit or tag to get past a failure. If a script fails,
report the failing step and the end of its output; then look for the cause.

Check each piece as its `README.md` says under "Commands" before going on.

### What only the person can do, or must approve

Stop and ask before each of these, naming exactly what you are about to do:

- **Writing the SD card.** `dd` to the wrong device destroys a disk. Show the person the
  output of `lsblk` and have them confirm the device name. Never guess it.
- **Any flash operation** (`install-flash.md`). Reading the flash back stops the running
  system; writing it can leave the board unable to start until it is written again over JTAG.
  Do the read-back first and make sure the person has put the file somewhere safe before the
  write.
- **Shutting down or restarting the board.**
- Plugging cables, swapping the card, power cycling, and looking at the HDMI picture are theirs
  to do; say plainly what you need and wait.

Stage 1 changes nothing on the board itself: the card that came with the board, kept aside,
is the way back. Stage 2 changes the flash; `install-flash.md` has the way back.

### Report what happened

Say what you built, what you checked and how, and what you could not check. Some paths in
this repository have not been run yet (the table in `README.md`): if you are the first to run
one, say so, and say whether it worked.

## Changing the repository

- No names of private machines, addresses, accounts or passwords, in files or in commit
  messages. This repository is public.
- Commit messages: a short subject and, for anything of substance, a body saying what
  changed and why. No attribution or "generated by" trailers (`.claude/settings.json` turns
  them off for Claude Code).
- Keep the "What has been tested" table in `README.md` true. Move a row to "yes" only for
  something that was actually run, and say on what.
- Every piece's `README.md` keeps the same headings in the same order: what it produces, what
  it needs first, tools to download, source, commands. Its diagram and its text must agree
  with its `build.sh`.
- The FPGA design is changed in `fpga/` (the Tcl scripts, `top-level.patch`, our own files),
  never in the applied copy. After a change: run `fpga/sim/run.sh` if the video block changed,
  run `fpga/build.sh` from a clean `work/agilex5-ed-hps-baseline`, then make the fork's
  branch again as `fpga/README.md` describes. The fork's branch is never edited by hand.
- `top-level.patch` is against Altera's files as the Tcl scripts leave them, not against
  Altera's originals: the scripts add lines to the `.qsf` first.
- A change to the FPGA design that changes what the processor routes to the FPGA
  (`tcl/hps_connections.tcl`) changes the first-stage image, so boards need their flash
  written again. A change to the logic alone does not. Say which it is.
- The frame buffer's address and size are written in one place, `fpga/src/hdmi_scanout.sv`.
  The device tree overlay takes them from there; do not write them anywhere else.
- Pushing, creating repositories, and anything else that others can see: only when the
  person has said yes to that action.
