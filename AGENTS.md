# Instructions for agents

This repository takes a Terasic DE25-Nano from source to a running Debian system. You may be
here to build it for someone, or to change the repository. Read `README.md` first: it says
what this is. `build.md` says what the two stages are and has what the build needs, the
tasks and the order of work.
`how-it-works.md` explains the parts specific to this repository: the boot arrangement, and
the hardware support provided through the FPGA. Each task's own `README.md` has what it
produces, what it needs first, its tools, its source and its commands.

## Building it for someone

Before starting, check the machine and say what is missing: Docker usable by this user, git,
free disk (about 10 GB), for the SD image on x86 `ls /proc/sys/fs/binfmt_misc/ | grep
aarch64`, and for stage 2 Quartus Pro of the version in `fpga/QUARTUS_VERSION`
(`fpga/q quartus_sh --version` finds it or says it is missing).

Quartus Pro has to be installed by the person: getting its installer needs their account
with Altera, and it is a 17 GB download and 38 GB on disk. Do not change
`fpga/QUARTUS_VERSION` to match a version the machine happens to have.

Order:

- `make -j3 test` builds whatever is out of date, in the right order, and tests the image in
  QEMU. Run it as a background job and report its lines as they come. After a change, run
  it again: it rebuilds only what the change affects. The tasks one at a time:
- Tasks B, K and F are independent until the last step of Task F. Start them together, as
  background jobs, and report as each finishes: `u-boot/build.sh`, `kernel/build.sh`,
  `fpga/build.sh` (stage 2 only).
- `fpga/build.sh` needs `out/u-boot/u-boot-spl-dtb.hex` only for its last step. If Task B has
  not finished by then it stops with a message; run it again and it carries on.
- `packages/build.sh` next, then `sdimage/build.sh` last. Without Task F they make only the
  tools package, and the image without the boot package and the core.
- Do not edit a build script while it is running: the shell reads it as it goes.
- A new file that a task is made from needs no entry in the Makefile if it is in the task's
  directory; a dependency on another directory does.

The scripts fetch sources into `work/` and write results to `out/`. Do not edit what is under
`work/`, and do not change a pinned commit or tag to get past a failure. If a script fails,
report the failing step and the end of its output; then look for the cause.

Check each task as its `README.md` says under "Commands" before going on.

### What only the person can do, or must approve

Stop and ask before each of these, naming exactly what you are about to do:

- **Writing the SD card.** `dd` to the wrong device destroys a disk. Show the person the
  output of `lsblk` and have them confirm the device name. Never guess it.
- **Any flash operation** (`install.md`, `flash-jtag.md`): `sudo de25-fpga select` when it
  says the flash will be written, `sudo de25-fpga flash-write`, `sudo de25-fpga
  flash-restore`, and anything over JTAG. Never pass `--yes` for the person. A write that
  fails part-way leaves the board unable to start until the flash is written over JTAG.
  After a write from the board, have the person copy `saved-<crc32>.rpd` from the
  card to somewhere else.
- **Shutting down or restarting the board.**
- Plugging cables, swapping the card, power cycling, and looking at the HDMI output are theirs
  to do; say plainly what you need and wait.

Stage 1 changes nothing on the board itself: the card that came with the board, kept aside,
is the way back. Stage 2 changes the flash; `install.md` has the way back.

### Report what happened

Say what you built, what you checked and how, and what you could not check.

## Changing the repository

- No names of private machines, addresses, accounts or passwords, in files or in commit
  messages. This repository is public.
- Commit messages: a short subject and, for anything of substance, a body saying what
  changed and why. No attribution or "generated by" trailers (`.claude/settings.json` turns
  them off for Claude Code).
- Every task's `README.md` keeps the same headings in the same order: what it produces, what
  it needs first, tools to download, source, commands. Its diagram and its text must agree
  with its `build.sh`.
- Altera's words for the two parts of the FPGA design: the HPS image (phase 1, in the flash)
  and the core image (phase 2, on the card). The SPL is U-Boot's first stage, in the HPS image.
- After a change to `packages/fpga-tools/de25-fpga`, run `packages/fpga-tools/test.sh`, and
  keep its man page true. Raise the versions in
  `packages/VERSIONS` as `packages/README.md` says.
- The FPGA design is changed in `fpga/` (the Tcl scripts, `top-level.patch`, the added files),
  never in the applied copy. After a change: run `fpga/sim/run.sh` if the video block changed,
  run `fpga/build.sh` from a clean `work/fpga/base`, then make the
  applied design's branch again as `fpga/README.md` describes. That branch is never edited by hand.
- `top-level.patch` is against Altera's files as the Tcl scripts leave them, not against
  Altera's originals: the scripts add lines to the `.qsf` first.
- A change to the FPGA design that changes which SoC peripherals are routed to the FPGA
  (`tcl/hps_connections.tcl`) changes the SoC settings in the HPS image, so boards need
  their flash written again, and core images built before it no longer load: the build
  fails until `fpga/hps-settings.txt` and `fpga/BOOT_NAME` are dealt with as
  `fpga/README.md` says under "The SoC settings". A change to the logic alone does not.
  Say which it is.
- The three hooks in the top level (`fpga/ext/`), the signals they may use, and the layout
  of a derived design's directory are an interface that other repositories build on. Do
  not change them without saying so; `fpga/example` must keep building.
- The frame buffer's address and size are written in one place, `fpga/src/hdmi_scanout.sv`.
  The device tree overlay takes them from there; do not write them anywhere else.
- Pushing, creating repositories, and anything else that others can see: only when the
  person has said yes to that action.
